# Phase 6 — Money and Auto Apply

Companion to [README.md](./README.md) §15, which says what phase 6 is in three lines. This is the
design: every table, every rule the ledger enforces, every client file that changes, and the
reasons for each deviation from the plan.

**Written for:** whoever builds or reviews this phase, including someone who has read none of the
earlier phase documents.

**Exit condition (from §15):** *a user subscribes, generates a draft, reviews it, applies, and the
ledger balances.*

**Status:** met on the local stack. `npm run verify:phase6` passes 106 checks, 0 failures, with one
real draft generated by `claude-sonnet-5` (§7).

---

## Decisions taken for this phase

Four questions were put to the product owner before building; the rest were settled in the build
and are argued below.

| # | Question | Chosen | Consequence |
|---|---|---|---|
| A | Where does the ledger live? | **In Postgres, as functions the app calls** | §2.1 predicted "the credit ledger" would land in the API service. Every rule turned out to be a transaction over one user's rows — nothing needs a secret — so the balance, the daily grant and the streak bonus are RPCs, like phase 2's interactions. §3. |
| B | How is "one a day" paid? | **Lazily, in 24-hour periods since sign-up** | No nightly job, no timezone, no calendar date for a client to lie about. Proven to pay exactly what a nightly job would. §3.1. |
| C | How far does billing go? | **Server-side in full; the SDK in Expo Go's Preview mode** *(owner's choice)* | The webhook, `subscriptions`, `entitlements` and the state machine are built and verified with fixture events. Real store purchases need a development build and a RevenueCat project. §4.3. |
| D | What does Pro buy? | **More Auto Applies and a bigger shelf** *(owner's choice)* | Free: 1/day, bank 5, 3 resumes. Pro: 5/day, bank 25, 10 resumes. All six numbers are rows in `plans`, not code. §4.1. |
| E | Where do a form's questions come from? | **Greenhouse's real form; a standard set elsewhere** *(owner's choice, corrected)* | The owner chose "real where public" expecting Greenhouse **and Ashby**. Ashby's documented API has no form; only Greenhouse does. §5.1. |
| F | Which model drafts? | **Sonnet 5, configurable** *(owner's choice)* | Measured at **$0.011 per draft**, 6–8 s. Every run logs tokens and `cost_usd`. §5.4. |
| G | When is a credit committed? | **At the hand-off, not at "I applied"** | §6 says "user confirms they submitted → credit committed". Taken literally, every draft is free to anyone who never confirms. §5.3. |
| H | Does a draft store the reader's name? | **Never, and the model never sees it** | Contact fields are opened from the sealed columns at read time, logged, and never written to `auto_apply_runs`. §5.2. |

## 0. What phase 6 is, in one paragraph

Until this phase the Auto Apply balance was a `useState` seeded with one credit. The streak bonus
was paid by a `useRef<Set>` that forgot every week it had paid when the app restarted. Tapping
Auto Apply decremented a number and opened the same hand-off sheet a plain Apply opens, so the
credit bought nothing. Phase 6 makes the credit real on both ends. The balance is a sum over an
append-only ledger with an idempotency key on every row. What a credit buys is a drafted
application: the posting's own questions, answered from the parsed resume, every field reviewed
by the reader before they copy it onto the employer's form. And there is a paid plan whose only
source of truth is a webhook from the store.

## 2. Tables

| Table | Holds | A reader can select | A reader can write |
|---|---|---|---|
| `plans` | Every number a plan changes | all rows | nothing |
| `credit_transactions` | The ledger | own rows, minus the idempotency key | nothing — functions only |
| `subscriptions` | One row per account that ever subscribed | own row, minus store ids | nothing, ever |
| `entitlements` | What an account is allowed | own rows | nothing, ever |
| `billing_events` | Every webhook delivery, verbatim | nobody | nothing |
| `auto_apply_runs` | Runs, forms, drafts, cost | nobody — through the API | functions only |

`idempotency_key` is withheld from the ledger's grant because it embeds the user id. That's
harmless on a reader's own rows, but it's still an identifier with no screen that needs it.

`auto_apply_runs` is unreadable directly for the reason `resumes` is (PHASE4.md §4.2): a run
only means something once its contact fields are resolved, which only the service can do. A
second read path returning the same row with holes in it would be a second thing to keep correct.

## 3. The ledger — decision A

§2.1 listed "the credit ledger (§7)" among what would land in the API service. It did not, for
the reason every earlier phase gave for keeping something in Postgres: the rule needed neither a
secret nor a model. The ledger's rules are all "read one user's rows, decide, insert one row, in
one transaction". Postgres does exactly that, and the service would have to reach back to
Postgres for every one of them. So `my_credits()`, `claim_streak_bonus()`, `review_auto_apply()`,
`complete_auto_apply()` and `abandon_auto_apply()` are RPCs the app calls directly, and the
service calls `start_auto_apply()` only because a model call follows it.

**One lock.** Every function that writes the ledger first takes `lock_ledger(user)`, a
`select … for update` on the reader's `profiles` row. A balance that is a sum is only correct if
no two writers can both read it before either inserts. The profile row exists for everyone, is
one row, and nothing hot writes it. The verify script races eight reservations against a balance
of one: exactly one is charged, and the balance ends at zero.

### 3.1 The daily grant is lazy — decision B

§7 describes a job that runs daily with key `grant:{user_id}:{YYYY-MM-DD}`. Two things are wrong
with that for this app:

- **A date needs a timezone.** UTC midnight is 5pm in California. The reader's own date comes
  from the client, and a client can claim tomorrow's date today.
- **A nightly job over every account** writes 50k rows a night for accounts that mostly aren't
  looking. If the job silently stops, nobody gets a credit, and nothing alerts.

So the grant is **claimed on read**, in **24-hour periods counted from the moment the account was
created**. Key: `grant:{user}:{period}`. `my_credits()` claims before it answers, and the app
reads its balance whenever it comes to the foreground, so opening the app in the morning is
when the morning's credit arrives. `next_grant_at` is exact, and the UI can say it.

**It pays exactly what a nightly job would.** The worry with lazy accrual is that missed days bank
beyond the cap. A reader sits at the cap of five for ten days, spends down to zero, and is paid
ten. That can't happen, for two reasons:

1. Every function that changes the balance claims first, under the same lock. From the ledger's
   point of view, no time passes between a claim and the next write.
2. A claim at the cap still writes a row, with **amount zero**, recording the periods it consumed.
   `credit_transactions_sign` allows zero for grants for this reason.

So a reader two below the cap who is away ten days comes back to the cap (a nightly job: the
same). A reader at the cap comes back to the cap with the gap recorded as consumed (a nightly
job: ten wasted grants, the same outcome). The verify script checks both.

### 3.2 A reservation is a spend row

§6: "reserved then committed or refunded — never decremented optimistically". The ledger form of
that with the fewest states is:

| Moment | Ledger | Run |
|---|---|---|
| Reserve | `spend:{run}` −1 | `pending` |
| Commit | *(nothing)* | `reviewed` |
| Refund | `refund:{run}` +1 | `failed` / `abandoned` |

There is no "reserved" amount for a sum to get wrong, the balance is right at every instant, and
a retried refund is a no-op because its key is the run id. The client never decrements anything.
After a reservation or a refund it re-reads `my_credits()`.

### 3.3 The streak bonus is paid by the server

The client's `awardStreakBonus(weekKey, amount)` took the amount as an argument. A client that
can name the amount can name three. `claim_streak_bonus(week)` takes only the week, and the
server decides:

- the week is a Monday, no newer than tomorrow and no older than three weeks;
- it met the reader's `weekly_goal`, counted from `applications.applied_at`;
- how long the streak is, walking back week by week (bounded at a year);
- what that is worth under the reader's plan, capped at `max_weekly_bonus` and at the bank.

`earned` and `awarded` are both returned. A full bank pays less than a week was worth, and the
card's "Bank full — spend some first" depends on knowing the difference.

§7's anomaly rule is taken literally. If twenty of the week's applications were logged within
ninety seconds, the outcome is `held`. The key isn't written, so the week can still be paid by
support or a later rule. It is just not paid automatically.

## 4. Subscriptions

### 4.1 `plans`, and why a gate never reads `subscriptions`

§8: "Every gate checks `entitlements`, not `subscriptions`." This phase adds one indirection so
the numbers are data too: `plans.id` **is** the entitlement identifier. A reader is on `pro`
exactly when they hold an unexpired entitlement named `pro`. That is also what the entitlement is
called in RevenueCat's dashboard, so the dashboard, the webhook's row and the gate all use one
string. `viewer_plan()` is the single function that answers the question. The daily grant, the
bank cap, the streak numbers and `register_resume`'s shelf limit all read from it.

A promo is an `entitlements` row with `source = 'promo'`. A store event never overwrites or
expires one, so a support grant can't be undone by a lapsed subscription.

### 4.2 The webhook

`POST /webhooks/revenuecat` checks the shared secret in constant time and forwards the event to
`apply_revenuecat_event()`. RevenueCat doesn't sign bodies; it echoes back an `Authorization`
value you configure. The function holds the entire state machine:

| Event | Status | Access |
|---|---|---|
| `INITIAL_PURCHASE`, `RENEWAL`, `UNCANCELLATION`, `PRODUCT_CHANGE`, `SUBSCRIPTION_EXTENDED`, `TEMPORARY_ENTITLEMENT_GRANT` | `active` | until `expiration_at_ms` |
| `NON_RENEWING_PURCHASE` | `active`, no renewal | until expiration |
| `CANCELLATION` (auto-renew off) | unchanged, `auto_renew = false` | until expiration |
| `CANCELLATION` with `CUSTOMER_SUPPORT` (a refund) | `refunded` | ends now |
| `BILLING_ISSUE` | `grace` | until expiration, which includes the store's grace period |
| `SUBSCRIPTION_PAUSED` | `paused` | until expiration |
| `EXPIRATION` | `expired` | ends |
| `TRANSFER` | moves the source account's rows | — |
| `TEST`, anything else | logged, `ignored` | — |

Four rules sit on top, each checked by the verify script:

- **Redelivery is a no-op.** The event id is `billing_events`' primary key.
- **Order is not trusted.** An event older than the last one applied to that account returns
  `stale`. A retried `RENEWAL` can't resurrect an `EXPIRATION`.
- **A lapse deletes nothing** (§8). The subscription row, the expired entitlement, every resume
  over the free limit, and every credit stay. The limit stops the *next* resume.
- **The account is found through every id RevenueCat knows.** `app_user_id`,
  `original_app_user_id`, then `aliases`. That way a purchase made before `Purchases.logIn()`
  still lands. An event matching nobody is `unmatched`, logged, and answered 200, since a retry
  can't make it match.

A new subscriber also gets one Pro day immediately (`subscription_grant`, keyed by original
transaction). Otherwise the current period's grant has already been paid at the free rate, and
someone who just paid sees nothing change until tomorrow.

**Why not call RevenueCat's REST API on each webhook**, as RevenueCat suggests: the payload carries
the product, the entitlements, the expiration and the timestamp, which is everything these rules
read. Fetching the subscriber would add a second secret and a network call inside a webhook
handler to learn the same facts. The trigger for revisiting is in §1.

### 4.3 The client, and Expo Go — decision C

`lib/billing.ts` is the only file that touches `react-native-purchases`, the way `lib/api.ts` is
the only file that knows how jobs are fetched. It can show offerings, run a purchase and restore.
**It cannot grant anything.** After a purchase, the paywall polls `my_credits()` until the
webhook has written the plan, and says "activating" until then.

In Expo Go the SDK detects the environment and runs in **Preview API mode**. Offerings and the
purchase sheet are JavaScript mocks, no purchase reaches a store, and so no webhook ever arrives.
The paywall says so. This is the owner's chosen scope: everything that can be proven without a
store is proven (§7), and the rest is configuration (§9).

## 5. Auto Apply

```
tap Auto Apply
  → POST /v1/auto-apply          start_auto_apply(): lock, one live run per posting, parsed
                                  resume required, claim grant, balance > 0, insert run + spend
  → form                          Greenhouse ?questions=true, else the standard set  (§5.1)
  → draft                         one forced tool call, Sonnet 5                     (§5.4)
  → save_auto_apply_draft()       pending → ready, cost logged whatever the status
  ← the run, contact fields resolved and logged                                     (§5.2)
review every field in the sheet
  → review_auto_apply(seen, edited)   ready → reviewed; the credit is committed      (§5.3)
  → the employer's form opens; the reader copies answers across
"I applied"
  → complete_auto_apply()         reviewed → used; writes the tracker row with its run id
"Discard" before the hand-off
  → abandon_auto_apply()          → abandoned; refund
```

### 5.1 Where the questions come from — decision E

**Greenhouse** publishes each posting's application form through the same public Job Board API
the crawler already reads: `GET /v1/boards/{token}/jobs/{id}?questions=true`. A live check
against Figma's board while building returned 18 fields: the contact block, the resume upload,
"Why do you want to join Figma?", work authorization, a location question, and the EEOC block.
The board token comes from the posting's crawl source, or from its apply URL when it came
through the Simplify aggregator.

**Everybody else gets the standard set**: contact, resume, location, school, degree, graduation,
LinkedIn, website, work authorization, sponsorship, start date and "why this company". The owner
chose "real where public" on the understanding that Ashby also publishes forms. It doesn't.
Checked against a live board, Ashby's documented posting API returns title, location,
compensation and description, and no form. Ashby does run an undocumented GraphQL endpoint with
the form in it, and §4.3 is explicit that the crawler reads published APIs. A better draft isn't
worth changing the legal posture. Lever's v0 postings API has no form either, and Workday's forms
sit behind per-tenant accounts.

A Greenhouse fetch that fails, times out or parses to nothing answerable falls back to the
standard set. A draft against the common questions is still worth the credit; a failed run is
not.

**Three roles are never drafted.** `contact` is filled at read time (§5.2). `attachment` is the
reader's own upload. **`self_identify`** covers EEOC and demographic questions, and pronouns
wherever they appear. These are always left for the reader and never shown to the model.
Inferring a protected characteristic from a resume would be the worst fabrication §6 forbids.

### 5.2 Contact fields are never stored — decision H

PHASE4.md sealed name, email and phone at parse time and said they would be "first read in
phase 6". They are read here, and only here:

- **The model never sees them.** It drafts "why this company" from skills, education and
  experience. It has no use for a phone number, and a prompt containing one is a copy of P0 data
  in a vendor's request log.
- **The draft never stores them.** `draft` holds `{source: "contact", value: null}` for each.
  `GET /v1/auto-apply/:id` opens the sealed columns on every read, writes a `pii_access_log` row
  with purpose `autoapply` first, and fills them into the response only. A leaked
  `auto_apply_runs` table leaks answers to "why this company", not identities.
- **Without a sealed value, the account is the fallback.** The profile's own name and the sign-in
  email are things the reader typed into CareerDeck themselves.

The verify script checks that the stored row contains none of the three values, while the
response carries all of them.

### 5.3 The credit commits at the hand-off — decision G

§6 draws "user confirms they submitted → applications row + credit committed" and "user
abandons → credit refunded". Built literally, a draft is free to anyone who never taps "I
applied". Generate, copy every answer, close the sheet, and the refund arrives. The model call
still happened.

The credit buys the draft, so it is committed when the draft is used: at the hand-off, when the
reader has seen every field and opened the employer's form (`review_auto_apply` moves the run
to `reviewed`). Before that, closing the sheet abandons the run and refunds. After it, closing
means "not yet" and the run stays open for "I applied". Abandoning a reviewed run is allowed, and
closes it so the posting can be drafted fresh, but refunds nothing.

`review_auto_apply` also requires `seen` to cover every key in the draft. A client can lie about
that, and the doc does not pretend otherwise. It is a durable record that the product showed
every field, in the spirit of `content_policy_accepted_at`. It also catches the honest bug: a
sheet that stopped rendering one field type would otherwise commit credits on drafts nobody saw.

**The sweep** (`expire_auto_apply_runs`, in `scripts/maintain.mjs`) fails and refunds runs stuck
`pending` for fifteen minutes, meaning the service died mid-draft. It abandons and refunds drafts
nobody opened for a week. It never touches `reviewed` runs.

### 5.4 The drafter, and what it costs — decision F

`server/src/autoapply/draft.ts` is the extractor's shape again: one call, a forced tool call
back, adaptive thinking at medium effort. The prompt names the questions a model is most tempted
to answer, so they come back null with a prompt every time: work authorization, sponsorship,
start dates, salary, links, attestations. `normalize()` then enforces mechanically what a prompt
can only request:

- an answer to a question that wasn't asked is dropped;
- a select answer that isn't one of its options becomes null;
- anything marked `inferred` is capped below `high` confidence;
- a skipped question arrives as null with a prompt.

**Measured**, on the verify script's standard-form posting over three runs:
**2,133 input + 651–681 output tokens ≈ $0.011 per draft**, 6.5–8.1 s. It declined work
authorization, sponsorship and LinkedIn every time, and wrote a 60–150-word "why this company"
from the resume's actual skills, flagged `low` or `medium`. At the free plan's 30 credits a month
the worst case is ~$0.33 per active free user per month. A Pro user spending all 150 costs ~$1.65.
Those are the numbers to price against. A Greenhouse form with a dozen custom questions will cost
more, and `cost_usd` per run is what will say how much.

Sonnet 5 and not Opus 5 is the owner's choice, made on this basis. The draft is text in and text
out with no PDF to lay out, and the parse (still Opus) has already done the reasoning-heavy
reading. `AUTO_APPLY_MODEL` switches it, and `prompt_version` plus `model` on every row make a
before/after comparison a query.

## 7. Verification

```
npm run db:reset
# the service, pointed at the local stack, with REVENUECAT_WEBHOOK_AUTH set:
SUPABASE_URL=http://127.0.0.1:54721 SUPABASE_ANON_KEY=… SUPABASE_SERVICE_ROLE_KEY=… \
  PORT=8799 REVENUECAT_WEBHOOK_AUTH=some-secret node --env-file-if-exists=.env server/src/index.ts
CAREERDECK_API_URL=http://127.0.0.1:8799 REVENUECAT_WEBHOOK_AUTH=some-secret npm run verify:phase6
```

**106 checks, 0 failures**, including the exit condition end to end. Alice's account runs the
full flow: its grant backfills to the cap, she subscribes by webhook, gets a live Sonnet 5 draft,
reviews it, hands off, applies, and ends with a ledger of `daily_grant +5, subscription_grant +5,
spend −4, refund +3 = 9`. Every spend maps to exactly one run, every refund to a failed or
abandoned one, and the sum equals `my_credits().balance`.

It spends about a cent per run. Without `ANTHROPIC_API_KEY` in the service, the live draft is
skipped and the closing line says the exit condition is **not** proven, as phase 4's did.

**Caught in review, before the first run:** four PL/pgSQL variables shadowed column names
(`amount`, `outcome`, `feature`, `source`). In `update billing_events set outcome = outcome`, the
right-hand side resolves to the variable or errors depending on context. All four were renamed,
but this is the bug class to watch for in every function here.

**Caught by verification:**

- **A bulk fixture insert wrote explicit nulls.** PostgREST takes the union of every row's
  columns, so one closed posting with a `status` made every other posting's `status` null.
- **The first "…and nobody else's" check measured a grant, not RLS.** It filtered by `user_id`,
  which isn't a granted column, so the query errored and the check's `!error` failed. It would
  have passed just as wrongly if the column were granted. It now compares what Bob can see
  against what Bob owns. This is phase 5's lesson again: a check has to fail for the reason it
  names.

**Earlier phases, rerun on this branch:** phases 2, 3 and 5 pass. Phase 5's "no new routes"
check named `/auto-apply` the day it landed, which is what it was written to do. `/auto-apply`
is now in its expected set, with a comment, rather than the check being loosened. Three
failures seen along the way predate this phase:

- **Phase 3's realtime check** failed once with nothing arriving in 8 s, then passed on a rerun.
- **Phase 5's `job_card.rank` checks** fail rather than skip when the fresh account hashes into
  the control arm, where rank is correctly null.
- **Phase 4's parse check** fails on the local storage-api `42P10` defect. It used to be skipped
  because this machine had no API key; now it has one, and there's no object to parse.

## 8. What it leaves behind

- **Two named triggers:** reconcile via RevenueCat's REST API on the first unexplained "I paid
  and nothing happened", and price Pro after a month of `cost_usd`.
- **`plans` and `constants/goal.ts` must change together.** The constants are copies for first
  paint, and nothing detects drift between them except a reader seeing a number the server
  doesn't honour.
- **The hosted project is three migrations behind** once this merges: `20260927`, `20260928` and
  `20260929`. Until `supabase db push` runs, the app against the hosted project shows a balance of
  zero (the query falls back), and Auto Apply fails with a 500 because `start_auto_apply` does not
  exist there.
